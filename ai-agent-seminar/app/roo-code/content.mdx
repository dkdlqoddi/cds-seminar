## Roo Code가 뭔가요?

**Roo Code**는 VS Code(에디터)에 설치하는 무료 확장입니다. 설치하면 사이드바에
채팅창이 하나 생기고, 거기에 한국어로 일을 시키면 **현재 열려있는 폴더 안에서**
파일을 읽고, 코드를 짜고, 명령을 실행해줍니다.

비슷한 도구로 Cursor, Cline, GitHub Copilot Chat 등이 있지만, Roo Code의 장점은:

- **VS Code에 그대로 붙는다** — 별도 에디터 설치 불필요
- **OpenAI Compatible 서버를 1급 시민으로 지원** — 사내 게이트웨이를 그대로 붙일 수 있음
- **모드 전환이 명확** — Code / Architect / Ask / 커스텀 모드를 직접 선택

## 우리가 쓰는 LLM 백엔드: 사내 GPT-OSS 게이트웨이

본 세미나는 OpenAI/Anthropic 같은 외부 API를 쓰지 않습니다. 대신 사내에 이미
구축되어 있는 **GPT-OSS 게이트웨이**를 사용합니다.

| 항목 | 값 |
| --- | --- |
| 종류 | 사내 API 게이트웨이 (사내망 한정 접근) |
| 인터페이스 | **OpenAI Compatible** (`/v1/chat/completions` 호환) |
| 호스트 (Stage) | `apigw-stg.samsungds.net:8000` |
| 서빙 모델 | `openai/gpt-oss-120b` |
| 인증 | 표준 Bearer 아님 — 사내 발급 **`x-dep-ticket`** 헤더 |

<Callout kind="info" title="왜 외부 API가 아니라 게이트웨이인가">
- 측정 데이터/도면/사내 코드가 **외부 클라우드로 빠져나가지 않습니다**.
- 사내 인증/감사 로그가 게이트웨이 한 곳에서 일괄 관리됩니다.
- 사용량/비용이 부서 단위로 추적됩니다 — 개인 카드로 OpenAI 계정 만들 필요 없음.
</Callout>

## 사전 준비

<Callout kind="check" title="시작 전 체크리스트">
1. **VS Code**가 설치되어 있다 ([code.visualstudio.com](https://code.visualstudio.com))
2. **`x-dep-ticket`** 자격증명을 발급받았다 (사내 AI 플랫폼 포털에서 발급, 사번 기반)
3. **사용자 ID**(`User-Id` / `User-Type`로 사용할 사번 또는 메일)를 알고 있다
4. **시스템 명**(`Send-System-Name`)을 안내받았다 (예: `CDS_Infra_SW`)
5. **작업할 폴더**가 하나 정해져 있다 (예: `D:\projects\measurement-cleanup`)
</Callout>

ticket 발급/시스템 명 등록은 사내 AI 플랫폼팀의 안내를 따라 미리 끝내두세요.

## 8단계 설치 가이드

### 1) VS Code 열기

처음이라면 [code.visualstudio.com](https://code.visualstudio.com)에서 다운로드 후 설치합니다. 한국어 패치는 첫 실행 시 자동으로 권유됩니다.

### 2) Roo Code 확장 설치

왼쪽 사이드바의 **확장(Extensions)** 아이콘(네모 4개) → 검색창에 `Roo Code` → **Install**.

설치가 끝나면 사이드바에 새 아이콘(캥거루 모양)이 추가됩니다. 클릭하면 채팅창이 열립니다.

### 3) 작업 폴더 열기

상단 메뉴 **파일 → 폴더 열기**로 작업할 폴더를 엽니다.
**중요**: Roo Code는 "현재 열려있는 폴더"의 파일만 보고 수정합니다.
회사 비밀자료 폴더를 통째로 열면 그 전부에 접근할 수 있다는 뜻이므로,
**작업 단위로 폴더를 분리해 두는 습관**이 필요합니다.

### 4) Provider를 "OpenAI Compatible"로 설정

Roo Code 채팅창 우상단 **설정(톱니바퀴)** → **Provider** 드롭다운 → **`OpenAI Compatible`** 선택.

<Callout kind="warn" title="Ollama 옵션을 고르지 않는다">
Provider 목록에 "Ollama"가 따로 있지만, 본 세미나의 사내 게이트웨이는 **vanilla Ollama가 아니라 OpenAI Compatible 인터페이스**를 따르므로 반드시 **OpenAI Compatible**을 선택해야 합니다. Ollama 옵션을 고르면 인증 헤더 형식이 달라 호출이 모두 실패합니다.
</Callout>

### 5) Base URL 입력

`.env.local`의 `BASE_URL`은 `…/v1/chat/completions` 까지 적혀 있는데,
Roo Code의 OpenAI Compatible Provider는 **`/chat/completions`를 자동으로 붙이므로
그 앞부분(`/v1`)까지만** 입력합니다.

| .env.local의 BASE_URL | Roo Code Base URL 칸에 입력할 값 |
| --- | --- |
| `http://apigw-stg.samsungds.net:8000/gpt-oss/1/gpt-oss-120b/v1/chat/completions` | `http://apigw-stg.samsungds.net:8000/gpt-oss/1/gpt-oss-120b/v1` |

### 6) Model 입력

**Model** 칸에 `.env.local`의 `MODEL_NAME` 값을 그대로 입력합니다.

<CodeBlock
  filename="Roo Code → Settings → OpenAI Compatible"
  lang="text"
  code={`Base URL:  http://apigw-stg.samsungds.net:8000/gpt-oss/1/gpt-oss-120b/v1
Model:     openai/gpt-oss-120b
API Key:   credential:TICKET-xxxxxxxx-...   ← 발급받은 ticket 전체를 그대로 붙여넣기`}
/>

<Callout kind="info" title='왜 API Key 칸에도 ticket을 넣나'>
표준 OpenAI Compatible 클라이언트는 입력된 키를 `Authorization: Bearer …`로 전송합니다. 게이트웨이는 이 Bearer 헤더를 무시하지만, 빈 칸이면 Roo Code가 요청 자체를 보내지 않을 수 있어 같은 ticket 값을 그대로 넣어두는 것이 안전합니다.
</Callout>

### 7) Custom Headers 등록 — 가장 중요한 단계

게이트웨이는 표준 Bearer 인증이 아닌 **커스텀 헤더 4종**을 요구합니다. Roo Code의
**Custom Headers** 영역(설정 화면 하단)에 다음을 추가합니다.

| 헤더 이름 | 값 | 설명 |
| --- | --- | --- |
| `x-dep-ticket` | `credential:TICKET-xxxxxxxx-...` (`API_KEY` 값 전체) | **실제 인증 키** |
| `Send-System-Name` | `CDS_Infra_SW` | 호출 시스템 식별 |
| `User-Id` | `your.id@samsung.com` (사번/메일) | 호출자 식별 |
| `User-Type` | (User-Id와 동일) | 감사 로그용 |

### 8) 첫 프롬프트로 연결 확인

채팅창에 다음을 입력해 봅니다.

<CodeBlock
  lang="text"
  code={`현재 폴더에 어떤 파일들이 있는지 알려줘.`}
/>

Roo가 `list_files` 도구를 호출하고 결과를 한국어로 요약해주면 연결 성공입니다. **401/403** 이 떨어지면 ticket 값 또는 System-Name이 맞는지 다시 확인하고, **404**가 떨어지면 Base URL 끝의 `/v1` 까지만 적었는지 확인합니다.

## 알아두어야 할 게이트웨이의 한 가지 까다로운 점

`.env.local` 동봉 예제(`ollama_example.py`)를 자세히 보면 매 요청마다 **새 UUID** 인 `Prompt-Msg-Id`, `Completion-Msg-Id` 헤더를 보내는 것을 알 수 있습니다.

<CodeBlock
  filename="ollama_example.py 발췌"
  lang="python"
  code={`headers = {
    'x-dep-ticket'      : api_key,
    'Send-System-Name'  : system_name,
    'User-Id'           : user_id,
    'User-Type'         : user_id,
    'Prompt-Msg-Id'     : str(uuid.uuid4()),     # ← 매 호출마다 새로 생성
    'Completion-Msg-Id' : str(uuid.uuid4()),     # ← 매 호출마다 새로 생성
    'Accept'            : 'text/event-stream; charset=utf-8',
    'Content-Type'      : 'application/json',
}`}
/>

<Callout kind="warn" title="Roo Code 환경에서의 한계">
Roo Code의 Custom Headers는 **정적**입니다. 매 호출마다 다른 UUID를 자동 생성하지는 못합니다. 게이트웨이가:

- 두 UUID를 **선택 헤더로 취급**한다면 → Custom Headers 비워두면 끝.
- **정적 더미 UUID를 허용**한다면 → Roo Code Custom Headers에 임의의 UUID 한 번만 등록.
- **반드시 매번 새 UUID를 요구**한다면 → Roo Code로는 정직하게 호출이 어렵습니다. 그 경우 [예제 5](/examples/direct-api)의 Python 직접 호출 패턴을 사용하세요.

사내 인프라팀에 정확한 정책을 한 번 확인해두면 향후 디버깅이 쉬워집니다.
</Callout>

## 절대 하지 말 것

<Callout kind="warn" title="사내에서 Roo Code 쓸 때 5가지 금기">
1. **Auto-approve를 켜둔 채로 자리 비우기** — 위험한 명령이 자동 승인될 수 있습니다.
2. **루트 폴더(`C:` 또는 `~`) 통째로 열기** — Roo가 의도치 않은 파일까지 건드릴 수 있습니다.
3. **개인 OpenAI/Anthropic 키로 우회** — 회사 데이터가 빠져나갑니다. 게이트웨이 외 백엔드 금지.
4. **`x-dep-ticket`을 git/Slack/문서에 붙여넣기** — ticket은 본인 사번으로 묶인 자격증명입니다. 누설 시 본인이 책임을 집니다. `.env.local`만 사용하고 절대 커밋하지 마세요.
5. **`rm -rf`, `git push --force` 같은 위험 명령에 대한 자동 승인** — 항상 수동 확인.
</Callout>
